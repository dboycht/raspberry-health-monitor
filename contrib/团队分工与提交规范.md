# 贡献与团队协作规范

> 面向**一起做这个课设的同学**：怎么分工、怎么改代码不打架、怎么提交。
> 技术细节见 [`../docs/04-驱动开发规范与贡献指南.md`](../docs/04-驱动开发规范与贡献指南.md)。

## 1. 分工总原则：一个器件 = 一个文件 = 一个人

```
rpi/health_monitor/
├── hal/        ← 契约层（**谁都不要改**，除非全组同意并同步文档）
├── sensors/    ← 每人认领自己的文件，互不 import
├── outputs/    ← 同上
├── core/       ← 业务逻辑（报警规则/采集调度/存储）——建议 1~2 人统一负责
└── net/        ← HTTP 接口（与安卓组对接）
```

**为什么不会打架**：业务层只认"驱动名 + 数据模型"，不认识任何具体器件类。
所以：
- A 同学的传感器没写好 → 用 `playback.py` 里的模拟器顶上，B 同学的显示模块照样能联调；
- 换器件型号 → 改 `config/devices.json` 一行，业务代码不动。

## 2. 三条铁律

1. **不碰别人的文件**。要改别人的驱动，先在群里说一声（避免两个人同时改同一个文件产生冲突）。
2. **不改契约层**（`rpi/health_monitor/hal/`）。确需修改 → 先改
   `docs/02-接口规格说明书.md` + `docs/CHANGELOG-接口.md` → 通知全组 → 再改代码。
3. **提交前跑全量测试**：`python -m pytest -q` 必须全绿（不是只有你的测试绿）。

## 3. Git 用法（小团队最省事的做法）

- **一个分支到底**：都往 `main` 提交，提交前先 `git pull --rebase`。
  （不建议给每个器件开分支——课设规模小，合并成本比收益高。）
- 提交粒度：**一件事一个 commit**（写完一个驱动 + 它的测试 = 一个 commit）。
- 提交信息格式：`<范围>: <做了什么>`

```powershell
git pull --rebase
git add rpi/health_monitor/sensors/dht11.py rpi/tests/sensors/test_dht11.py
git status --porcelain        # 确认没有 data/、日志、缓存混进来
git commit -m "sensors(dht11): 实现单总线读取与缓存策略"
git push
```

**绝不要 `git add -A` / `git add .`**：容易把 `data/`、`*.log`、`__pycache__/` 一起提交。
（`.gitignore` 已覆盖大部分，但请提交前自己看一眼 `git status`。）

**禁止入库**：`data/`、`*.db`、`*.log`、`__pycache__/`、`.venv/`、`DEVELOPMENT.md`、`ERROR.md`。

## 4. 冲突了怎么办

| 情况 | 做法 |
| --- | --- |
| 两人改了同一个文件 | `git pull --rebase` 时冲突 → **一起看**，不要盲目 `--theirs`；我们的规则是"谁负责该文件，以谁的为准" |
| 不确定怎么解 | 先 `git stash` 保命，把当前状态贴到群里，别硬解 |
| 提交错了（把 data/ 提上去了） | **立刻说**，用 `git rm --cached <file>` + 补一个提交；不要 `push --force`（会覆盖别人的提交） |

## 5. 联调约定

- **接口变了要通知安卓组**：改 `net/web.py` 就必须同步 `docs/05-安卓通信协议.md`。
- **加/改报警码要通知全组**：手机端文案表、LCD 英文文案、语音播报文案三处都要跟着改
  （清单在 `docs/08-报警规则表.md`）。
- **谁能改 `config/devices.json`**：建议指定 1 人（通常是负责整机装配的人），
  避免多人同时改引脚配置导致"我这边好好的、你那边全挂"。

## 6. 每周合练（建议）

1. `git pull` → `python -m health_monitor selfcheck --mock` → 看有没有 FAIL；
2. `python -m health_monitor demo` → 看全链路是否还通；
3. 有硬件的同学接上自己那块，跑 `selfcheck --real`；
4. 把"真机实测通过"的器件在 `docs/03-器件任务书.md` §7 进度表里打勾。

> ⚠️ **"单测通过" ≠ "真机通过"**。单测证明代码逻辑对；真机才能证明**接线、地址、时序**对。
> 进度表里两列要分开填。

## 7. 问问题的方式（省时间）

提问时带上这三样，别人一看就能答：

1. **你跑了什么命令**（完整命令，包括 `cd` 到哪）；
2. **完整报错**（不是"报错了"，而是错误类型 + 消息 + 关键几行栈）；
3. **你已经排除了什么**（例如"`i2cdetect -y 1` 能看到 0x57"）。

对应到本项目，很多问题的答案就藏在驱动报错信息里——
我们刻意把排查线索写进了 `DeviceInitError` 的文案（例如会提示你跑 `i2cdetect -y 1`）。
